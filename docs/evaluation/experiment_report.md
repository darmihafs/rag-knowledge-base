**现象与分析**

- 总体（92 题，Top-10 窗口）：混合检索 Hit@1 70.65%、Hit@3 86.96%、Hit@5 90.22%、MRR 0.799。Hit@1 相对词法路高出 14.13 个百分点、相对语义路低 5.43 个百分点；MRR 由词法 0.669 / 语义 0.821 变为 0.799，Hit@5 由 81.52% / 91.30% 变为 90.22%。三路里总体的 Hit@1 与 MRR 都由纯语义向量最高（76.09% / 0.821），混合检索没有超过它，因此本实验不能把混合策略表述为「全面最优」，只能按类别论证它的补位价值（见下一条与 3.3）。
- A 类（字面精确，平均字面重合度 46.30%）：词法 Hit@1 71.43%、语义 89.29%、混合 82.14%，MRR 0.827 / 0.946 / 0.902。词法路预期的优势在本组没有拉开，原因在实验尺度：语料只有 80 段，每个专有名词基本只在自己的那一段里出现，问题向量与目标段的余弦相似度足以压过其余段落，向量路等价地完成了「精确匹配」。这说明词法召回的价值不在于小语料下能不能命中术语，而在于语料规模上去、同一术语散布到多段之后仍能提供可控的硬特征区分——这一优势无法在 80 段的教学级评测集上被放大，属于本实验的尺度局限（见第 6 节）。
- B 类（同义改写，平均字面重合度仅 17.94%）：词法 Hit@1 48.57%、Hit@5 68.57%，语义 57.14% / 80.00%，混合 51.43% / 82.86%，MRR 0.579 / 0.645 / 0.663。混合路在这一类上同时压过两路（Hit@5 80.00% → 82.86%，MRR 0.645 → 0.663）：同义改写削掉了字面特征，但两路的排序信息并不相同——RRF 把「词法勉强命中」与「语义高度相似」这两个弱信号叠加成一个强信号，正确切片因此被顶进名额。
- C 类（术语与泛化并存）：三路 Hit@5 依次为词法 82.76%、语义 96.55%、混合 89.66%，MRR 0.625 / 0.914 / 0.866。这类问题上混合路的 MRR（0.866）没有超过最优单路（0.914），说明当两路都能稳定命中时融合不再带来名次收益；RRF 的真实价值集中在「某一路彻底失效」的题上，见 3.3 的逐题统计。
- 耗时：词法路平均 16.859 ms（P95 28 ms，只做数据库 LIKE 扫描，不调用任何外部服务），语义路平均 141.12 ms（P95 201 ms）、混合路 152.522 ms（P95 221 ms）。混合路并不比语义路多一次远程调用：两路各自只对问题做一次向量化，增量 11.402 ms 来自两组候选的回表与 RRF 排序，相对生成阶段动辄数秒的端到端耗时可以忽略；词法路虽快，但它单独承担召回时的质量损失（见上）远不是这点耗时能补偿的。

### 3.3 两路互补性的逐题证据

以 Top-5 为口径对 92 题逐一比对：

- 两路都在名额内命中的题目之外，**只有词法路**做到的有 4 题：B4、B5、B18、B32；**只有语义路**做到的有 13 题：B1、B6、C6、C7、A25、B12、B14、B15、B23、B25、B27、C12、C21。两者互不覆盖，正是「互补而非包含」的直接证据。
- 两路都掉出名额的有 4 题：B9、C5、B24、B31，其中混合检索救回 1 题：B24——RRF 让两路的弱信号叠加后重新进入候选，这是任何单一路都做不到的。
- 在两路表现不一致的题目上，混合检索相对最优单路**提前**的有 2 题：B24、B31，**退后**的有 11 题：B5、B6、C6、A25、B12、B14、B15、B25、B27、C12、C21。可见融合不是无损的：当某一路给出高分命中、另一路用一堆弱命中把名次拉平时，正确切片可能被挤出首位，这也是混合检索 Hit@1 未必高于单路的原因。

**现象与分析**

- 粒度从 200 字放宽到 1200 字时，切片总数由 162 降到 24，召回候选池随之缩小。粒度越粗，评测窗口在语料中所占的比例越高——最粗的 1200 字档只剩 24 段候选，Top-10 覆盖 41.67% 的候选，Hit@5 的区分度明显下降；因此本实验以 Hit@1 与 MRR 判断优劣，并用 Top-5 平均字数反向衡量 Prompt 成本。
  - 200 字：162 段，混合检索 Hit@1 59.78%、MRR 0.705、平均耗时 144.293 ms、Top-5 平均字数 757.924。
  - 500 字：58 段，混合检索 Hit@1 65.22%、MRR 0.761、平均耗时 149.772 ms、Top-5 平均字数 1769.663。
  - 800 字：31 段，混合检索 Hit@1 64.13%、MRR 0.754、平均耗时 140.293 ms、Top-5 平均字数 3293.272。
  - 1200 字：24 段，混合检索 Hit@1 61.96%、MRR 0.745、平均耗时 134.967 ms、Top-5 平均字数 4793.12。
- 纯语义路最能说明粒度的代价：200 字档把语料切成 162 段，一条完整知识被切分边界拆散后，问题向量只能与局部内容相似，Hit@1 只有 55.43%、MRR 0.654；换到 500 字档则升到 61.96% / 0.715。反之在 1200 字档，候选只剩 24 段，评测窗口 Top-10 已覆盖 41.67% 的语料，Hit@5 90.22% 这类数字的区分度随之下降，只能看 Hit@1 与 MRR。
- 大切片把整节内容塞进一个向量，主题被平均化、区分度下降，同时 Top-5 平均字数从 757.924 涨到 4793.12（6.324 倍），直接进入 Prompt 的无关文本成倍增加，token 成本与「注意力稀释」风险同步上升。
- 平均耗时对粒度的敏感度不高（144.293 ms → 134.967 ms），差值主要来自候选集大小与回表条数，而非切分本身；这说明工程上不必为性能选粒度，应当为召回质量选粒度。
- 四档里混合检索 MRR 最高的是 500 字 / 75 字重叠一档（MRR 0.761、Hit@1 65.22%），该档位与生产默认的 chunk-max-chars=800 / overlap=120 不同，选型时应在论文里说明取舍。Prompt 成本随粒度单调上升，命中率与 token 开销之间必须显式权衡（结论第 3 条给出对照）。

## 5 结论

1. 三条路的失分位置并不相同：词法路 Hit@5 最低的类别是 B 同义改写（68.57%），语义路最低的是 B 同义改写（80.00%），
   混合路三个类别里最差的 Hit@5 也有 82.86%（B 同义改写）。也就是说没有任何单路能同时兼顾字面硬特征与语义泛化，但本批数据里总体最优的是纯语义向量（Hit@1 76.09%、MRR 0.821），混合检索为 70.65% / 0.799，因此论文里不能把混合策略表述为「全面最优」；它的价值要按类别论证——混合同时在 Hit@5 与 MRR 上超过两路的类别是：B 同义改写（Hit@5 68.57% / 80.00% → 82.86%，MRR 0.579 / 0.645 → 0.663）。
2. RRF 只用名次不用原始分数，规避了「词法命中词数」与「余弦相似度」量纲不可相加的问题，
   代价只有一次候选合并与重排；k=60 使两路名次差异被平滑，但平滑是双向的：一路把正确切片顶到前列、另一路只贡献一堆弱命中时，名次同样会被拉平——本批混合检索 Hit@1 70.65% 低于最优单路 76.09%（5.43 个百分点），说明融合不是无损的，这个代价应当与收益一起写进论文。
   逐题层面的补位与救回统计见 3.3。
3. 切片粒度不存在对所有指标同时最优的取值：小片段提高语义纯度但割裂完整知识，
   大片段扩大候选池噪声并成倍增加进入 Prompt 的字符数。四档里混合检索 MRR 最高的是
   500 字 / 75 字重叠（Hit@1 65.22%、MRR 0.761、Top-5 平均字数 1769.663），
   而生产默认配置是 chunk-max-chars=800 / overlap=120，二者不同，若以 MRR 为选型依据，应把默认参数调整到 500 字一档，或在论文中如实说明当前默认值的选择理由。
4. 检索耗时远低于大模型生成耗时（流式问答端到端通常在秒级），因此召回阶段的策略取舍
   应以质量为主、性能为辅。本实验的词法路是「H2 内存库 + 逐词 LIKE 扫描」口径（平均 16.859 ms），
   该开销会随语料行数线性上升，因此生产已把词法路切到 ngram 全文索引
   （`rag.lexical-mode=fulltext` + `MATCH ... AGAINST ... IN BOOLEAN MODE`），
   十万级切片下的 LIKE / 全文索引延迟对照见 `docs/bench/lexical_ab_results.csv`。

## 6 局限与注意事项

- 命中判定采用「证据片段包含」而非切片 ID 比对：切片粒度变化后同一条标注仍然有效，但极短的证据串若恰好被切分边界劈开，会造成假阴性；`query_level_results.csv` 的 `evidence_in_corpus` 列记录了每题证据在该粒度下是否仍可整段命中，`answerable_queries` 列已把不可判定的样本从分母中剔除。
- 语料规模（80 段）仍远小于生产库，评测窗口 Top-10 约占候选池的 12.50%，Hit@5 的天花板效应已随候选池变大而减弱，因此跨策略比较应以 Hit@1 与 MRR 为准；候选池偏小还会让词法路残留的通用 2-gram 噪声更容易凑出命中，语料规模继续扩大后词法与语义的差距才会被充分放大。
- 跑批本身不含随机项：词法打分、余弦相似度与 RRF 排序都是确定性的，同一份语料与问题集重跑，Hit@K 与 MRR 不会变化，只有耗时字段抖动；若论文需要置信区间，可多次执行跑批后按 `config + strategy` 合并 CSV 再统计。语义路耗时受公网调用延迟影响明显，与本地词法路的耗时不可直接等价比较，因此本实验以召回质量为主要论证对象。
- 向量库为一期内存实现（序列化到本地 JSON），十万级语料下的性能与召回表现需另行验证。
- 词法路耗时是「H2 内存库 + 80 段候选 + 逐词 LIKE 扫描」口径下的数字，与生产 MySQL 十万级语料不可直接比较；生产默认 `rag.lexical-mode=fulltext`（ngram 全文索引 + MATCH AGAINST），两种词法实现的性能对照见 `docs/bench/lexical_ab_results.csv`。
- 语料与问题集为人工构造，规模 80 段 / 92 题，属于教学级评测集，不代表公开基准（如 DuReader、MS MARCO）上的可比结果。

## 8 复现方式

```bash
mvn -o -Dmaven.repo.local=<本地仓库> test -P benchmark -Dtest=RetrievalBenchmarkTest
```

评测执行器是一个受系统属性开关控制的 JUnit 用例（`kb.benchmark=true` 时才执行），普通 `mvn test` 会连同 benchmark 包一起排除，因此不会拖慢日常构建，也不会在无密钥的 CI 环境里失败。数据集为 `src/test/resources/benchmark/corpus.json` 与 `queries.json`，全部语料与切片写入 H2 内存库、向量写入 `target/benchmark-embedding-store.json`，不会接触开发库 `kb_rag`。重新跑批会覆盖本报告与三份 CSV，表格与正文数值自动同步。
