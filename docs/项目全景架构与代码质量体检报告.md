### 2.1 表清单（schema.sql 已是合并 V2–V10 的最终结构，9 表，InnoDB / utf8mb4 / utf8mb4_general_ci）

| 表 | 用途 | 核心字段与约束 |

### 2.2 表间关联（文字 ER，全库 0 物理外键）

`FOREIGN KEY|REFERENCES` 在 backend/src 全量 grep 零命中，以下全部是**逻辑外键**，删除一致性靠代码：

- kb_space 1→N kb_document（space_id）；kb_document 1→N kb_chunk（document_id）
- sys_user 1→N kb_space（created_by）、1→N chat_session（user_id）
- sys_user N↔N kb_space 经 kb_space_member（uk_space_user）

- 代码级联：删会话连带删消息（ChatSessionServiceImpl#deleteSession）、删文档删切片（KbDocumentServiceImpl）

### 2.4 H2 测试库差异（src/test/resources/db/schema-h2.sql）

- ChatFeedbackServiceImpl#pageForAdmin:130-134：仅按 rating 过滤时 idx_feedback_status(status,rating) 前缀不匹配；**issue_type 无索引**；order by id desc 无 (status,id) 类索引 → 主键倒扫+过滤或 filesort。

**无 LIMIT / COUNT 模式**：
- **ChatSessionServiceImpl#listSessions:59-62 无 LIMIT 全量拉取**——会话数随使用线性膨胀，前端下拉与内存一起涨。
- DashboardServiceImpl#stats:68-70 三次无条件 selectCount(null)（chunk 全量 COUNT 随语料线性变慢）。

- ChatFeedbackServiceImpl#stats:203-223：六次独立 COUNT + **拉全部点踩行进内存分组**（rating 单列无索引）。
- UserProfileServiceImpl#myStats:93-109 / UserAdminServiceImpl#countActivity:202-217：先取全部 sessionIds 再两次 IN+role COUNT，IN 随会话数膨胀。
- 所有 selectPage 自带 COUNT（MP 分页插件），深分页双重开销。

### 3.1 完整调用链（类#方法级）

1. **上传入口** `DocumentController#upload`（DocumentController.java:55）：`POST /api/documents/upload`（`POST /api/documents` 等价）、批量 `POST /api/documents/batch`。multipart：`max-file-size=50MB`、`max-request-size=200MB`（application.yml:26-27）。

3. **SHA-256 判重** `#sha256Hex`（:711，流式 8KB 缓冲）：查重维度 **spaceId+title+fileType+fileHash 四元组**（:143-148），命中抛 `BizException(4091)`（:150），不返回旧 ID。同内容改名可重复入库。
4. **落库初始状态** `save(doc)`：status=PENDING、chunkCount=0（:160-162）→ `spaceService.recount`。

7. **切块** `TextChunker#chunkWithOffsets`（TextChunker.java:40）：参数见 3.4；PDF 全局分块后按偏移映射页码（`KbDocumentServiceImpl#chunkWithPages`:581）。
8. **切片批量落库** `#persistChunks`（:516）：`Db.saveBatch(entities, CHUNK_BATCH_SIZE=500)`，与状态置 INDEXED 同在 `#publishIndexed` 的 `TransactionTemplate` 内（:543-567）。
9. **向量化（事务外）** `LocalAtomicFileVectorStore#indexChunks`（:248）：按 `rag.embedding-batch-size=10` 分批 `model.embedAll` → `embeddingStore.addAll`；模型 text-embedding-v3，**实测维度 1024**（运行时 store.json 核读；无维度配置项，`resolveDimension` 运行时探测，RagProperties:111 注释按 1536 估算内存——口径不符）。失败只 warn 返回已写条数，不抛异常。
10. **落盘** `#persist`（:608）：`synchronized(persistLock)` → 序列化到临时文件 store.json.tmp → `Files.move(ATOMIC_MOVE, REPLACE_EXISTING)`（:621），捕获 `AtomicMoveNotSupportedException` 回退普通 move。路径 `rag.embedding-store-path=./data/embeddings/store.json`。
11. **最终状态** 部分向量化失败 → `#markVectorizationIncomplete`（:669）：保持 INDEXED 但写 errorMsg 缺口提示，问答侧自动退化为词法检索。

### 3.4 切块算法（TextChunker）

- 参数：`rag.chunk-max-chars=800`、`rag.chunk-overlap-chars=120`；size=max(100,800)=800，stride=max(50,800-120)=**680**。
- 策略：`normalize` 统一换行+压缩空行 → 按 `\n\n` 段落聚合；**overlap 仅在超长段落滑窗模式生效**，普通段落聚合无重叠（即「跨页滑窗」实际是「超长段滑窗」，页边界靠 KBPAGE 标记映射页码，不按页切）。
- 上限：无最大块数限制（搜 maxChunks/MAX_CHUNK 无果），仅受 8M 字符总量间接约束。
- 评测敏感度实验四档 {200,30}/{500,75}/{800,120}/{1200,180}（重叠率均 15%），**实测最优档 500/75 与生产默认 800/120 不一致**（见 4.8）。

### 3.5 异常、重试与宕机恢复

- **解析/分块失败**：`#process` catch → `#fail()` 置 FAILED，errorMsg 截断 500 字存 `kb_document.error_msg VARCHAR(500)`，并删除半截切片。
- **向量化失败**：`indexChunks` 内部吞异常返回已写条数；`#process` 再兜底 catch（:334），文档仍 INDEXED，缺口写 errorMsg。
- **重试机制：【未实现】**（搜 `@Retryable/RetryTemplate/spring-retry/@EnableRetry/retryWhen` 全部无果；`retry` 仅命中 Redis 背避与「请稍后重试」文案）。唯一恢复手段是人工 `POST /api/documents/{id}/reindex`。
- **宕机恢复：【已实现】** `DocumentIngestRecovery#recoverInterruptedIngest`（:27，`ApplicationReadyEvent` 监听，亲读核对）→ `KbDocumentServiceImpl#requeueInterrupted`（:246-278，亲读核对）：查 PENDING/PARSING → PARSING 先条件退回 PENDING → 校验原文存在（缺失→FAILED）→ 重新入队（队列满→FAILED）。恢复失败只记日志不阻断启动。
- **恢复机制的两个真实缺口**（均有代码证据）：
  1. **崩溃窗口期向量丢失**：若宕机发生在 `publishIndexed` 已提交 INDEXED 之后、向量 `persist()` 之前，文档状态非 PENDING/PARSING，恢复扫描不会触及 → INDEXED 但向量缺失，无自动补偿（`requeueInterrupted`:247-250 只查两态）。
  2. **多实例启动会抢正在解析的任务**：`requeueInterrupted`:253-262 把 PARSING 无条件（仅按状态）退回 PENDING——实例 B 重启时会把实例 A 正在解析的文档重置并重新入队，导致双解析。条件 UPDATE 只防两个恢复者互抢，不防「恢复者 vs 活跃 worker」。单实例部署无此问题。

### 3.6 DB ↔ 向量库双写一致性

- **删除文档** `#removeDocument`（:391，@Transactional）：事务内删 chunk + 逻辑删 doc + recount；向量删除与磁盘原文删除排 `AfterCommitRunner.run`（提交后执行，回滚不删原文）。
- **重新解析** `#reindex`（:192）：事务内条件置 PENDING + 删旧切片；**事务外**调 `vectorStoreEngine.removeDocument`（:236）再入队。
- **切片编辑/启停/批量** `KbChunkServiceImpl#updateContent`（:82）/`#toggleStatus`（:109）/`#batchStatus`（:206，上限 500）：均 @Transactional 先改 DB，向量同步一律 AfterCommitRunner；禁用→removeChunk(s)，启用→indexChunks，编辑→先 remove 再按新正文 index。`removeChunks` 批量删完**只 persist 一次**，避免整库重写与条数成平方关系。
- **事务内远程向量化：不存在**（亮点）：所有 embedding HTTP 都在事务提交后或事务外；`publishIndexed` 用 TransactionTemplate 刻意把解析/embedding 排除在外。
- **真实缺陷（亲读源码证实）**：`indexChunks`:255-284 的 `persist()` 位于 try 内**整个循环之后**——若第 N 批 `embedAll` 抛异常，前 N-1 批已 `addAll`（:273）进内存的向量**永不落盘**，catch 只 warn 返回部分条数。内存与磁盘分叉，重启即丢这批向量，且无对账/修复入口。正确做法是每批成功后即 persist 或失败时回滚内存。
- 向量删除均 best-effort（失败仅 warn），DB 为准；孤儿向量靠回表 join 过滤，不影响召回正确性但会膨胀 JSON。

### 3.7 文件本体存储与预览安全

- 路径 `rag.upload-dir=./data/uploads`；命名 `{upload-dir}/{文档ID}/{yyyyMMdd}/{UUID去横线}.{ext}`（`#storagePath`:703），DB 存相对路径。
- **路径穿越防护：有**：`#resolveStoredFile`（:693）与 `#preparePreview`（:447）均 `root.resolve(...).normalize()` 后校验 `startsWith(root)`。
- 预览/下载 `DocumentController#preview`（:120，`GET /api/documents/{id}/preview`）：支持 HTTP Range（206），手写流拷贝避免整篇入堆；`X-Content-Type-Options:nosniff`；html 按 text/plain 返回防 XSS。权限 `#requirePreviewVisible`（:481）：空间授权 + 普通用户仅 INDEXED 可预览，admin 豁免。
- **无静态资源映射**（WebMvcConfig 无 addResourceHandlers），uploads 不经静态目录暴露。

## 4. 检索（RAG）、精排（Rerank）与评测体系细节

### 4.1 双路召回（RetrievalServiceImpl，292 行）

- **词法路** `#lexicalRetrieve`（:161）：`#buildTerms`（:266）小写化、去标点、CJK 长词(>4)切 2-gram、过滤单字中文词，上限 `MAX_TERMS=12`（:46）。默认 `rag.lexical-mode=fulltext`：走 `KbChunkMapper` 三条注解 SQL（searchByFulltext/InSpace/InSpaces，:28-95）——`MATCH(content) AGAINST(? IN BOOLEAN MODE) AS relevance`，`WHERE enabled=1`，`ORDER BY relevance DESC, document_id ASC, chunk_index ASC LIMIT ?`；词间空格=OR（`#booleanExpression`:258 剥操作符防注入）。SQL 抛 RuntimeException 自动降级 `#likeRetrieve`（:194）：逐词 `LIKE '%词%'` 分页取 topK*2，按**命中词数**打分降序，同分按 documentId/chunkIndex。
- **语义路**：`LocalAtomicFileVectorStore#searchChunkIds`（:530）embedQuestion → 空间前置过滤 → 余弦搜索（`rag.semantic-min-score=0.0`）→ 返回 chunkId；`#loadRanked`（:111）回表按名次重排。
- **Route 枚举**：LEXICAL / SEMANTIC / HYBRID。`#hybridRetrieve`（:88）：两路各取 `candidateK=topK*2`；scope 受限时语义路再 ×3（`SCOPED_SEMANTIC_FACTOR=3`，:52/:83）；融合后取 topK。纯 SEMANTIC 取 topK（受限 ×3）。

### 4.2 Pre-filtering 空间前置过滤（安全边界下推到存储层）

- `RetrievalScope` = record(spaceId, visibleSpaceIds)：`unrestricted()`=(null,null)、`ofSpace`、`visible`、`restricted()`、`deniesEverything()`（spaceId 为 null 且 visible 为**空列表**）。`retrieve` 入口（:63-70）：null→unrestricted；**空授权→warn+`List.of()`，绝不出网/查库**。
- `LocalAtomicFileVectorStore#spaceFilter`（:579-588）：单空间 `metadataKey("spaceId").isEqualTo`，集合 `isIn(visible)`；元数据由 `#toSegment`（:591）写入（chunkId/documentId/chunkIndex/spaceId）。
- **旧向量兼容**：升级前写入的向量无 spaceId 元数据 → 前置过滤空命中 → 退回无过滤**放大搜索** `maxResults*LEGACY_FALLBACK_FACTOR(=3)`（:542-548/:78）。
- **回表后置兜底**：`#loadRanked`（:115-122）restricted 时 `inSql(spaceSubquery)`（kb_document 按 space_id+deleted=0）并过滤 enabled=0；`#spaceSubquery`（:236）对空集合拼 `where 1=0` 双保险。安全性最终由后置过滤保证，前置过滤只是性能优化——契约在 VectorStoreEngine 接口 javadoc 里写明。

### 4.3 RRF 融合

`#rrfFuse`（:135-146）+ `#addRrfScores`（:149-154）：score=Σ1/(k+rank)，rank 从 1 起；**k=`rag.rrf-k`=60**；HashMap.merge 按 id 去重累加；排序=分数降序、**同分 id 升序（稳定）**，limit topK。**动态权重/查询意图路由：【未实现】**（src/main 全量 grep `weight|alpha` 零命中，两路权重恒 1.0）；唯一可调项 rrfK 支持运行时改（SystemConfigServiceImpl:64，校验 1~200）。

### 4.4 gte-rerank 精排流水线

- `RerankRetrievalService`（@Primary 装饰器，:59）：**只拦 HYBRID** 且 topK>0、question 非空、`isAvailable()`（=rerank.enabled && !mockEnabled && apiKey 非空），否则透传粗排——LEXICAL/SEMANTIC 单路消融保持「纯」，实验数据不被精排污染。
- `coarseK=max(topK, candidates=20)`（:65）；`keep=min(topK, topN=5)`（:72）。
- `DashScopeRerankClient`：POST 原生端点，Bearer 复用 rag.api-key；请求 `{model, input:{query,documents}, parameters:{top_n, return_documents:false}}`；解析 `output.results[{index,relevance_score}]`；带 code/缺 results/全无效→IllegalStateException；**index<0 或 ≥docCount→warn 跳过**（:170-174）；按 score 降序稳定排序（:181）；connect+read 各 3s，RestClient 按超时值缓存重建（:205-219）；Transport 接口供测试注入假传输。

### 4.7 量化评测模块（benchmark/RetrievalBenchmarkTest，716 行）

- **语料**：`src/test/resources/benchmark/corpus.json` **80 段人工构造**（grep 计数核实）：10 主题——Java与JVM/分布式/操作系统/数据库/系统架构/网络协议各 10，前端/安全/算法/检索与大模型各 5；18,321 字、平均 229.0 字/段。
- **题目集**：queries.json **92 题 = A28/B35/C29**（核实）：A=专名/参数/数字（考词法）、B=同义改写（考语义）、C=综合。`validateDataset` 校验 targetSection 存在且含 evidence、evidence 全库唯一。
- **实验一（消融）**：`seedNaturalCorpus` 一段=一 chunk（绕开分块器隔离变量），写 H2(MODE=MySQL)，真 OpenAiEmbeddingModel（60s 超时），向量落 target/benchmark-embedding-store.json。**四臂**：LEXICAL/SEMANTIC/HYBRID 基线（:189 强制关精排）+ HYBRID_RERANK 附加臂（开精排、topN=EVAL_WINDOW=10 同窗口公平对比、逐题 pacing 300ms 不计入耗时、预热 2 题后取 fallbackCount 基线，差值=降级题数）。
- **指标实现**：`EVAL_WINDOW=10`、`PROMPT_COST_K=5`；`retrieveOnce`（:307）rank=首个正文含 evidence 的名次（`content.contains(evidence)`，:314）；Hit@K=rank≤K 题数/可判定题数（:378）；MRR=mean(1/rank，未命中 0)（:364）；分母剔除证据被切分劈开的题（evidencePresent）；P95=ceil(0.95n)-1 分位（:386）。
- **实验二（切片敏感度）**：四档 {200,30}/{500,75}/{800,120}/{1200,180}（重叠 15%），同主题拼整篇经**生产 TextChunker** 重切、重向量化（校验写入条数），跑三路由，关精排隔离粒度变量。

## 5. Agent 循环、SSE 流式问答与并发护栏实现

### 5.1 Agent 循环与原生 tool_calls（AgentServiceImpl，633 行）

- 循环：`#run`（:469-527）`for round < task.maxSteps`；maxSteps 默认 4、限 1..5（`#prepare` + AgentAskRequest @Min(1)@Max(5)）；工具总次数硬上限 **`MAX_TOOL_CALLS=8`**（:59，已核对）。每轮：查 cancelled/expired → `chatModel.chat(ChatRequest…toolSpecifications(AgentToolCatalog.SPECIFICATIONS).maxOutputTokens(1800))` → 无 tool_calls 则 `#finishAnswer`；有则 `#validCallIds`（id 非空≤128 且去重）→ 追加 `AiMessage.from(calls)` → 逐个 `AgentRunState#execute`。
- 终止原因枚举 `AgentAskResponse.StopReason`：COMPLETED / NO_EVIDENCE（无证据或答案含固定句）/ STEP_LIMIT / TOOL_LIMIT / TIME_LIMIT（90s）/ CANCELLED / MODEL_ERROR。
- 接口：**原生 tool_calls**（LangChain4j 1.22.0 OpenAiChatModel，DashScope 兼容模式，qwen-plus，temperature 0.2，timeout 60s）；**无 ReAct 文本解析**（搜 ReAct/function_call 无果，类注释明示）。
- **恰好 3 个工具**（AgentToolCatalog:11/17/23，已核对；分发在 AgentKnowledgeTools#execute:48-51 switch）：

| 工具 | 参数（AgentToolArguments 强制白名单/类型/范围，raw≤2000，未知字段拒绝） | 干什么 |
|---|---|---|
| `search_knowledge` | query 必填 1..1000 字；limit 1..5 默认 3 | 调 RetrievalService.retrieve **HYBRID**（带精排）检索可见空间 |
| `list_documents` | keyword≤100 可选；limit 1..10 默认 5 | 列可见空间内 **仅 INDEXED** 文档（title LIKE） |
| `read_chunks` | documentId 必填正整数；startIndex 0..100000；limit 1..5 默认 3 | 读指定文档 **enabled=1** 切片正文，复核文档归属 |

- 回填：observation JSON（正文≤1200 字）经 `ToolExecutionResultMessage.from(call,…)` 入 messages；citations 按 documentId:chunkIndex 去重；每次工具完成即推 SSE `step` 事件；执行后 `#executeTask` **复核空间权限**，变更抛 4030（防「模型回调期间被撤权」）。

### 5.2 多轮记忆管理

- 表 chat_session/chat_message；`ChatSessionServiceImpl#loadRecentHistory`（:127-131）Page(1,limit) 按 id 倒序再反转正序；limit=`rag.history-messages=6`（**3 轮**）；每条经 `RagAnswerServiceImpl#appendHistory`（:430-438）abbreviate 到 `rag.history-max-chars=1200`。
- **无 token 预算、无摘要压缩：【未实现】**（搜 compress/summar/truncate/maxHistory/摘要/压缩，仅命中审计展示截断与分块器空白压缩）。同步 `/ask`（:90-109）传 List.of() **干脆不带多轮**。
- 写入：`#doStream` 先读历史再 `saveUserMessage`（@Transactional：insert+首问自动标题+updateTime）；回答在 onCompleteResponse → `#persistAssistant` → `saveAssistantMessage`（insert+citations JSON+会话时间），**落库成功才推 done**（带 messageId，失败为 null）；cancelled 则不落库。
- **Agent 无多轮记忆、无持久化**：`#run` 仅 System+本轮 question；任务/回答只存内存 `ConcurrentHashMap tasks`，**无 agent_task 表**（搜无此表），重启即丢，无审计落库。

### 5.3 SSE 流式输出与断连取消

- 入口：KnowledgeController `POST /api/knowledge/ask/stream`（produces TEXT_EVENT_STREAM），`SseEmitter(300_000ms)`；AgentController `POST /api/agent/ask/stream`，`SseEmitter(120_000ms)`；均设 `X-Accel-Buffering:no`、`Cache-Control:no-cache`；前端 fetch POST 消费（不用 EventSource）。
- 事件协议：knowledge=`meta{retrieved,topK,history,sessionId,mock}` / `delta{text}` / `citations[{documentId,title,chunkIndex,pageNumber,snippet,score}]` / `done{elapsedMillis,messageId}` / `error{code,message}`；agent=`meta{taskId,mock,maxSteps,timeoutMillis}` / `step{ToolStep}` / `done{AgentAskResponse}` / `error`。
- 模型回调：OpenAiStreamingChatModel（timeout 120s）+ StreamingChatResponseHandler（onPartialResponse/onCompleteResponse/onError）；Agent 用**阻塞** ChatModel，仅步骤级流式。
- **心跳：【未实现】**（全主代码搜 heartbeat/心跳/keep-alive/ping/comment( 零命中，已亲自复核）——检索阶段（embedding 20s+rerank 3s）与首 token 前无任何字节下发，反代空闲超时可断连（nginx 已配 proxy_buffering off + 300s 缓解，但公网中间层不可控）。
- 断连取消：knowledge 的 `AtomicBoolean cancelled` 定义于 `#askStream`（局部变量）；onTimeout→置位+complete，onError/onCompletion→置位；检查点：任务开始前、落库前、召回后、`#streamText` 每增量、三个回调内；`#send` 捕 IOException/IllegalStateException 抛 SseClosedException → cancelled.set(true)。Agent：AgentTask 内 cancelled/terminal/released 三个 AtomicBoolean；onCompletion/onTimeout/onError→`#cancelOnDisconnect`（cancel+future.cancel(true)+markTerminal+release）；`#run` 每轮头/模型返回后/每个工具前检查；step 回调遇 terminal 抛 AgentStreamClosedException；单线程看门狗 `#timeoutStream` 90s 强制收尾。
- **取消的真实语义（短板）**：RagAnswerServiceImpl:118-119 注释自认「StreamingChatModel 没有暴露取消句柄」——cancelled 只停**推送/落库**，模型流继续跑满（最长 120s），token 照烧；Agent `future.cancel(true)` 依赖中断，OkHttp 阻塞 chat（60s）未必响应中断，超时后最多多跑一次模型调用，且看门狗已 release 闸门，旧 worker 不占槽继续跑。

### 5.4 跨异步线程上下文传递

`UserContext` 是**普通 ThreadLocal**；**无 TaskDecorator/InheritableThreadLocal/TransmittableThreadLocal**（搜索无匹配），全靠**显式传参+手动 set/clear**：`#askStream` 在 Tomcat 线程抓 LoginUser 带入池任务（finally clear）；`#persistAssistant` 在 OkHttp 回调线程 set/恢复 previous；`AgentServiceImpl#executeTask` set(task.login)/finally clear；`#safePartial` 供看门狗线程显式 set；`AuthInterceptor#afterCompletion` 必 clear（:190-195）。清理纪律经抽查无遗漏——这是做对的部分。

### 5.5 并发护栏与降级（三层闸门）

`AgentServiceImpl#acquire` 顺序：
1. 进程内 `runningUsers` Set：单用户互斥，命中→4290；
2. `Semaphore slots=new Semaphore(rag.agent-threads=4)`：`tryAcquire()` 无等待，失败→回滚①→4290；
3. Redis `tryLock("agent:lock:"+userId, owner=taskId, TTL=kb.cache.agent-lock-ttl-seconds=90)`（SET NX EX）：**HELD**→slots.release+Set 移除→4290；**UNAVAILABLE**→保留本地闸门继续（降级不拒绝）；**ACQUIRED**→markDistributedLockHeld。

释放：`#release` 经 releaseOnce CAS 幂等，仅持锁标记为真才 Lua 解锁（get==owner 再 del，绝不误删他人锁）；释放在 executeTask/ask/timeoutStream 的 finally 与 cancelOnDisconnect。线程池 agentExecutor core=max=4、queue=32、AbortPolicy→4290。Redis 故障背避 10s、命令超时 2s。
**问答流式无每用户/每 IP 限流**：仅 ragStreamExecutor（4/16/100）满→4290；**同步 `/ask` 无任何闸门**；**登录防爆破【未实现】**（搜 RateLimit/限流/sliding/bucket/attempt/爆破，authenticate 只有密码比对，无失败计数/锁定/延迟）。

### 5.6 事务与流式交织

全部 13 处 @Transactional 均在 ChatSession/KbChunk/KbDocument/KbSpace/SpaceAccess/SysUser/UserAdmin；**RagAnswerServiceImpl、AgentServiceImpl 无事务注解**——SSE 推送与模型调用都在事务外，消息落库是短事务且在 done 推送前提交。非事务资源统一 afterCommit（AfterCommitRunner / RedisCacheService#deleteAfterCommit）。Agent 无 DB 事务，状态机在内存 AgentTask（publish 一次性终态，synchronized 保护）；顺序：prepare 校验→acquire（本地→Redis）→putIfAbsent（重复 4090 并 release）；异常先 publish 终态再 cancel worker（防 TIME_LIMIT 被 CANCELLED 覆盖）。
**锁 TTL 隐患（短板）**：锁在 prepare（submit 前）取得，TTL=90s 与任务预算 90s 等长，看门狗在 submit+90s 才收尾释放——**TTL 必然先到期**；RedisCacheService 只有 tryLock/unlock **无续期方法**。看门狗延迟或 worker 超时后仍在跑时，跨实例同账号可再获锁**双跑**。单实例有本地 Set 兜底，分布式部署即露馅。
